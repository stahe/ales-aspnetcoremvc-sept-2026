    6. Ámbitos de los datos

    Una aplicación web atiende a muchos usuarios a la vez, y cada usuario realiza numerosas solicitudes. Por lo tanto, los datos se pueden compartir en tres niveles, conocidos como su ámbito:

    • ámbito de aplicación: los datos los comparten todos los usuarios durante toda la vida del servidor (la lista de médicos, por ejemplo);
    • ámbito de solicitud: los datos existen solo mientras dura una solicitud (el modelo de una vista);
    • ámbito de cliente: los datos son específicos de un usuario y deben persistir de una solicitud a la siguiente (el idioma seleccionado, el usuario conectado).

    El curso original ([ASP.NET MVC], 2013) usaba una sesión para este último ámbito: un espacio de memoria, mantenido por el servidor, específico de cada navegador. [ASP.NET Core] sigue utilizando este enfoque ([AddSession]), pero este documento, al igual que el caso de estudio, prescinde de él: los datos de ámbito de cliente los almacena el navegador en cookies. El servidor no conserva ningún dato entre las solicitudes de un mismo usuario: se dice que no tiene estado ([stateless]). Esto es lo que permite, por ejemplo, ejecutar varios servidores idénticos detrás de un balanceador de carga. La contrapartida: una cookie está bajo el control del usuario, que puede leerla y modificarla. Por lo tanto, solo se almacenan allí datos no sensibles, o datos firmados o cifrados por el servidor, que puede entonces detectar cualquier modificación: es el caso de la cookie [TempData] (ejemplo 20) y del token de autenticación (capítulo 8).

    Del lado del servidor, los ámbitos de aplicación y de solicitud corresponden a los tiempos de vida de los servicios de inyección de dependencias (véase el ejemplo 06). [ASP.NET Core] tiene tres:

    Registro
    Tiempo de vida
    Una instancia...
    AddSingleton
    aplicación
    durante toda la vida de la aplicación, compartida por todas las solicitudes
    AddScoped
    solicitud
    por solicitud HTTP, compartida por todos los que la piden durante esa solicitud
    AddTransient

    namespace Example23.Services;

// ámbito de APLICACIÓN (AddSingleton): una única instancia, compartida por
// TODAS las solicitudes de TODOS los usuarios
public class CounterService
{
    private int total;

    // varias solicitudes pueden ejecutarse AL MISMO TIEMPO: Interlocked
    // garantiza que dos incrementos simultáneos no se pierdan
    public int Increment() => Interlocked.Increment(ref total);
}
    • Línea 7: el servicio será un singleton (véase [Program.cs]): su campo [total] tiene, por lo tanto, ámbito de aplicación;
    • línea 11: un servidor web procesa varias solicitudes simultáneamente, en varios hilos ([threads]). Si dos solicitudes ejecutan [total++] al mismo tiempo, ambas pueden leer el mismo valor y se pierde un incremento. [Interlocked.Increment] realiza la lectura, la suma y la escritura en una sola operación indivisible. Un servicio singleton debe desconfiar siempre de estos accesos simultáneos.

    namespace Example23.Services;

// ámbito de SOLICITUD (AddScoped): una instancia NUEVA por cada solicitud HTTP,
// compartida por todos los que la piden DURANTE esa solicitud
public class RequestService
{
    private static int createdInstances; // static: un contador compartido por todas las instancias

    public int Number { get; } = Interlocked.Increment(ref createdInstances);
}
    • línea 7: un campo declarado [static] pertenece a la clase, no a una instancia; lo comparten todas las instancias. Cuenta el número de instancias creadas;
    • línea 9: a cada instancia se le asigna un número al crearse. El servicio tendrá ámbito de solicitud: el número cambia con cada solicitud.

    using System.Text.Encodings.Web;
using System.Text.Unicode;
using Example23.Services;
using Microsoft.Extensions.FileProviders;

var builder = WebApplication.CreateBuilder(args);
builder.Services.AddControllersWithViews();

builder.Services.AddSingleton<CounterService>(); // una instancia para toda la aplicación
builder.Services.AddScoped<RequestService>();    // una instancia por solicitud
builder.Services.AddTransient<ToolService>();    // una instancia por inyección

var app = builder.Build();

app.UseStaticFiles(new StaticFileOptions
{
    FileProvider = new PhysicalFileProvider(Path.GetFullPath(Path.Combine(builder.Environment.ContentRootPath, "..", "common", "bootstrap"))),
    RequestPath = "/bootstrap",

// ámbito de SOLICITUD: HttpContext.Items nace y muere con la solicitud
app.Use(async (context, next) =>
{
    context.Items["start"] = DateTime.Now.ToString("HH:mm:ss.fff");
    await next(context);
});

app.MapControllers();
app.Run();

    using Example23.Services;
using Microsoft.AspNetCore.Mvc;

namespace Example23.Controllers;

public record ScopesModel(int Total, int Instance, int Tool, int MyVisits);

public class ScopesController(CounterService counter, RequestService request, ToolService tool) : Controller
{
    [HttpGet("/")]
    public IActionResult Scopes()
    {
        // ámbito de CLIENTE: un dato guardado por el NAVEGADOR (cookie),
        // reenviado al servidor con cada solicitud
        int.TryParse(Request.Cookies["myVisits"], out var myVisits);
        myVisits++;
        Response.Cookies.Append("myVisits", myVisits.ToString(),
            new CookieOptions { HttpOnly = true, SameSite = SameSiteMode.Lax });
        return View(new ScopesModel(counter.Increment(), request.Number, tool.Number, myVisits));
    }
}
    • línea 8: se inyectan los tres servicios;
    • líneas 15–18: el ámbito de cliente: un contador almacenado en una cookie. [Request.Cookies["myVisits"]] lee la cookie enviada por el navegador ([null] en la primera visita). [int.TryParse] la convierte en entero; si la conversión falla, [myVisits] se establece en 0. La acción lo incrementa y vuelve a establecer la cookie;
    • línea 19: los valores se pasan a la vista.

    Para un contador de visitas, esto es irrelevante. Para datos sensibles (la identidad del usuario, su rol), el servidor debe poder detectar la manipulación: el capítulo 8 muestra cómo.

    De estos tiempos de vida se desprende una regla: un servicio no debe depender de un servicio con un tiempo de vida más corto. Un singleton que recibiera un servicio como [Scoped] lo conservaría indefinidamente, mucho más allá de la solicitud para la cual se creó. [ASP.NET Core] verifica el cumplimiento de esta regla al iniciar, en modo de desarrollo, y se niega a arrancar si se infringe. En el caso de estudio:
